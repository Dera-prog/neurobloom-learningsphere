01 — The problem2 / 10

Three conversations,
none of them connected.

A secondary school in Nigeria usually runs on three separated conversations. Students learn in one place, teachers track progress in another, and parents hear about it at the end of term — if at all. For a child with ASD or ADHD, none of those three places is built for the way they learn.

The learner

One pace for everyone

Lessons, quizzes and reports assume the same speed for every child. Nothing on screen tells a struggling learner where they actually are.

The teacher

Tracking by memory

Marks live in a notebook, assignments in a chat, and attendance in a register. Progress conversations restart from zero each week.

The parent

Waiting for term

Fees paid, work handed in, silence in between. Parents cannot see attendance, effort or the support a child is getting.

The design brief was not “make a dashboard”. It was: give each of the six people in a child’s school life a place that shows them their part — and make those places tell the same story.

ConstraintWhat it forced
Phone-first audienceEvery surface designed at 390 px first; tables and consoles checked for horizontal fit, not just desktop.
Naira-priced subscriptionsFive plans from ₦2,500 to ₦25,000 a month, priced on a real cost base instead of a foreign tier list.
Small team, real productionOne shared design system and one state layer, so six experiences could ship without six codebases drifting apart.
Trust with parentsNumbers had to be measured, not invented — an empty state beats a plausible fake one.
Definition of done

A parent can see today’s progress without calling the school. A teacher can mark work without retyping it. An owner can read the platform’s real state without asking anyone — including me.

03 — The approach4 / 10

One system.
Six experiences.

The temptation with six dashboards is to design six products. I treated them as one system with six arrangements: shared components, shared state, shared theme tokens, different priorities.

  • One component library. Cards, tables, empty states, dialogs and form controls are shared, so a fix or accessibility pass lands everywhere at once.
  • One state layer. Plans, children, assignments and messages follow the account across devices instead of living in one browser.
  • Theme tokens, not theme forks. Light plus a per-role dark mode is a token swap — burnt orange, navy, purple, green, teal, grey — not six stylesheets.
  • Navigation by job. A parent never sees an assignment-marking tool; a teacher never sees billing. The sidebar is the role’s actual week.
What that bought

Six surfaces, one behaviour

Empty states, loading states, focus rings and mobile breakpoints were designed once and inherited. When a mobile popover overflowed by one pixel, it was one fix — not six.

The system also made later requests cheap: a new page in the parent portal reused the same shell, the same tokens and the same data hooks.

How the work actually moved

01 · Frame

Role first

Every request started as “who is looking at this, and what do they need to decide?” before any layout.

02 · Build

Ship in slices

Each slice went to production and was checked against the live bundle, not a local preview.

03 · Check

Test the rendered page

Automated browser passes at desktop and 390 px: tap targets, overflow, focus, empty states, stale data.

What I refused to do
Duplicate the themesSix stylesheets would drift on the first shared fix.
Split the codebasesOne deploy, one state layer, one design system.
Invent sample numbersAn honest empty state beat a convincing fake one.

05 — The money path6 / 10

Priced in naira,
resolved on the server.

Subscriptions are the one place where a browser must never be trusted. The client sends a plan id; the server holds the price list, applies the promo code and tells Paystack what to charge.

GeneralCore lessons, assignments and progress for one learner.₦8,500
PremiumAdds tutoring and the full subject library.₦15,000
Premium PlusEverything in Premium, with priority tutor access.₦25,000
Special Needs PremiumThe calm, adapted experience for ASD and ADHD learners.₦22,000
Parent Access add-onA second guardian gets the parent dashboard and progress digests.₦2,500
Decision

The price list lives on the server

Plan amounts and the discount table sit in the serverless function, keyed by plan id. A tampered request can change which plan it asks for, never what that plan costs. Promo codes — BLOOM10, FAMILY15, WAEC20 — resolve server-side too.

Decision

Paystack is the source of truth

Checkout initialises, the callback verifies, and a webhook re-syncs entitlements afterwards — so a closed tab or an interrupted redirect cannot leave a paid parent without access.

Add-on, not tier

Parent Access

Parents were the audience most likely to pay for visibility but least likely to buy a student plan. Modelling the second guardian as a ₦2,500 add-on on top of a Premium plan kept the main tiers simple and turned a family need into an upsell instead of a fourth subscription.

Client sends

A plan id and a promo code

No amount, currency or entitlement flag leaves the browser as a trusted value.

Server decides

Price, discount, access

The function looks up the plan, applies the coupon table, and only then talks to Paystack.

Architecture

The browser never touches admin data

The console sends its bearer token to a serverless function, which verifies it, checks the role is admin, and only then reads with the service key. Eight routed pages share one shell; an unknown route redirects instead of rendering a blank screen.

Honesty rule

If it can’t be measured, it says so

Mail without credentials, a test-mode payment key, a module with no live source — each is labelled as such. A plausible sample number under a real heading is a defect, not a placeholder.

What the console will not show
Projected growthNo forecast dressed up as a measurement.
Estimated revenueOnly payments Paystack has actually confirmed.
Vanity totalsA count that cannot be derived from data stays blank.

07 — Decisions & trade-offs8 / 10

Six calls that
shaped the build.

Each of these cost something. They are written down with the cost attached, because a case study that only lists wins is a brochure.

Resolve prices on the server

Why: a client that names its own price is a client that will eventually name ₦0. Cost: every pricing change is a deploy, and the client still needs a display copy that must be kept in sync. Effect: coupons and plans can only be changed in one trusted place.

Fix the role at signup

Why: one account should not be a student on Monday and staff on Tuesday. Cost: a genuine role change needs an admin action. Effect: navigation, permissions and theming can trust the role without re-checking intent on every page.

Show “not connected” instead of samples

Why: sample numbers hide broken integrations until a customer finds them. Cost: early screenshots look emptier than a demo. Effect: the console turned into a diagnostic tool — missing Mailgun credentials and a test-mode payment key were visible the moment they were opened.

One library, six themes

Why: six bespoke dashboards would drift and break in six different ways. Cost: some role-specific ideas had to be expressed as variants rather than forks. Effect: a mobile overflow bug was one fix; a new portal page was hours, not days.

Verify admin reads on the server

Why: the owner console sees every account on the platform; a browser holding that power is one stolen token from a breach. Cost: every console page round-trips through a function. Effect: admin data never leaves the server without a role check.

Deploy each slice before the next

Why: a local preview cannot reproduce the production bundle, the real auth session or the live data. Cost: slower apparent progress, more deploy cycles. Effect: defects surfaced on the URL a customer would actually open.

Every one of these made the demo less impressive and the product more trustworthy.

08 — Where it stands9 / 10

Live, with the
gaps named.

The build is deployed and running against production services. Some integrations are deliberately still in their test state, and the console says so rather than hiding it.

Live

Public site, accounts and six dashboards. Deployed on Vercel with Supabase auth and Postgres; role routing, theming, onboarding and per-user state working in production.

Live

Admin Manager and Super Admin consoles. Eight owner-level pages reading through a verified server function; admin-only data is never queried from the browser.

Test mode

Payments. The full checkout, verification and webhook path runs against Paystack’s test keys. Going live needs a live secret key, live plan codes and a redeploy — the code path is already in place.

Pending

Email. The endpoint reports email_not_configured until a Mailgun key and domain are set; confirmations currently stay in-app.

Known

Admin module data persists per browser rather than in Postgres, and class video is simulated UI with no streaming backend. Both are documented limits, not surprises.

Next

Physical-device QA is still manual; phone OTP and social sign-in need an SMS or OAuth provider.

What the console found on day one

Found

A test key on a live site

Checkout worked, but Paystack was still in test mode — visible as a status line instead of being discovered at a customer’s first payment.

Found

Email switched off

Send endpoints returned email_not_configured rather than pretending a confirmation had gone out.

Found

Admin data in the browser

Some module data persisted per browser, not in Postgres — named on the console so it could not pass for working storage.

09 — What I’d carry forward10 / 10

Six surfaces teach you
more than one screen.

Designing the same product for a child, a teacher, a parent and an owner is the fastest way to find out which parts of an interface are actually product decisions.

Lesson 01

Design the empty state first

Deciding “what does this look like when there is no data, or the integration is off?” before the happy path made honesty cheap instead of a retrofit.

Lesson 02

A theme is identity

The special-needs palette is not decoration. Calmer colour and fewer competing panels are the product for a child who finds busy screens hard.

Lesson 03

Consoles earn their keep with live data

A dashboard of beautiful charts over sample rows is a poster. The same screens wired to production became the tool that told me what was actually switched on.

Lesson 04

Ship, then look at it

Every slice was deployed and checked on the live bundle. Most of the real defects — a popover one pixel off on mobile, a stale theme, a clipped card — only appeared there.

Keep

Prices on the server, one design system, and empty states that tell the truth before the happy path does.

Change

Wire the real integrations before designing a console around them — the console is a better diagnostic than a design review.
